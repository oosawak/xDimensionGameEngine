# xDimension Game Engine v0.0.15 — 素材切り替え・Pixel Art 解像度・パーティクル座標修正

**開発基準：v0.0.14 → v0.0.15**。v0.0.13までの町、3マップ、18＋6軒の建物・室内、NPC、季節、時刻、木箱パズル、C-WASM物理を維持します。

## v0.0.15 の追加・修正

- **素材切り替えを復活**：設定 → `SPRITES / キャラクター素材` → `Haruka（新画像）` / `オリジナル（旧画像）`。どちらも5動作（待機／歩行／走行／ジャンプ／攻撃）を内蔵。選択したセットの画像のみ起動時にデコードします。切り替え時は一時的に新旧画像のデコードが重なる可能性があります。未使用のHaruka30動作は配布物に含みません。
- **Pixel Art 可変解像度**：ONで64〜512px／コマ（16px刻み）のスライダー。初期値160px。OFFでは512×512pxのCanvasへ高精細描画。どちらでもThree.js CanvasTexture自体をリサイズしないため、OFFで消える問題への対策を継続します。Pixel Artの解像度設定と素材選択はブラウザに保存します。
- **SPRITE INFO**：素材選択の直下に元画像の1コマ解像度、ゲーム用解像度、Pixel Art ON/OFF、処理解像度、拡大方式、アニメーションのFPSと枚数、WebP圧縮量およびRGBAアトラス展開容量の概算を表示。実際のGPU消費量ではありません。
- **パーティクルの追従不具合修正**：プレイヤーの座標に粒子全体の親オブジェクトを毎フレーム合わせる処理を廃止。粒子の位置はワールド基準で保持し、プレイヤーが領域の端に進んだ際だけ放出領域を再中心化。既存粒子は相対座標を逆補正し、領域を出た分を循環配置。WebGPU computeとWebGL fallbackの両方へ適用しました。
- **既存個別調整**：素材別に倍率・位置の設定を保存。Harukaの既存調整を引き継ぎ、旧素材は以前の調整キーを再使用。世界時計などの保存データには変更ありません。

### 画像寸法

| 種類 | 元画像1コマ | ゲーム用1コマ | RGBAアトラス5枚の展開量（概算） |
| --- | --- | --- | --- |
| Haruka | 768×768px（攻撃1536×1536px） | 512×512px | 約125 MiB |
| オリジナル | 256×256px（攻撃512×512px） | 512×320px | 約78 MiB |

描画用Canvasは常に512×512px。**元画像／ゲーム用画像／最終的な画面上のピクセル数は異なる**ため、SPRITE INFOでそれぞれ表示します。

./build.sh rust         # Rustがある場合（未検証）

# xDimension Game Engine v0.0.14 — Haruka 5動作・高精細表示とPixel Art切り替え修正

**正式な開発基準: xDimension Game Engine v0.0.13**。HD-2D Lab v0.7で試した画像素材管理を必要な部分だけ移植した版です。v0.7を正本にしていません。

## v0.0.14 の主な変更

- `haruka_apps_all.zip` 収録の35動作から **idle / walk / run / jump / attackの5動作だけ**を採用。他30動作は配布物に含めていません。
- `assets/characters/haruka/` に5種類の元PNGとアトラス座標JSONを保存し、`assets/sprites.json` を切り出し・身体サイズ・足元位置の定義に使用。ビルド時に自動WebP化します。
- 出力画像を**1フレーム512×512px**に変更（v0.7の320×320pxから改善）。`index.html` にビルド時に埋め込みます。
- **Pixel Art OFF（初期状態）**: 512×512pxで高精細表示。**ON**: 約171×171pxに落としてからドット絵風に復元して表示。切り替え時にキャラクターが消える問題を修正。
- 根本原因: `CanvasTexture` が参照するCanvasを切り替え時に再リサイズしていたこと。これをやめ、GPUが参照するCanvasを512×512で固定。中間の縮小用Canvasだけを使う方式に変更しました。
- メモリ目安：ゲーム画像の**デコード後RGBAアトラス5枚で約125MiB（2560×2560×4×5）**。表示の`CanvasTexture`は512×512×4≒1MiB。実測GPUメモリではなく画像寸法に基づく理論値であり、ブラウザ内部のコピー・描画リソースは別途使用します。35枚を読み込む構成ではありません。
- **個別スプライト調整UI**は従来の倍率・XY位置・JSON書き出しを継続。Haruka用の保存キーを新設し、旧画像の調整設定を上書きしません。
- ジャンプ110%、攻撃85%の初期倍率、操作ボタン常時表示、初期折りたたみUI、WebGPU/WebGL切替、高台・階段・家18軒・3エリア・季節・NPC・パズル2箱を維持。

## v0.0.13 — WASM物理判定付き押し箱パズル

- **実際に操作できる試作パズル**：エリア0の「こもれび街道」東側（X=6〜10、Z=29〜32）の広場に木箱2個と床スイッチ2個を配置。すべての木箱をスイッチ上に置くと祭壇が光ります。中央の森道は通行可能なままです。

- **制限**：現段階は1か所2箱の試作。スイッチによる扉開閉や複数マップ別パズルは今後の拡張対象。RustソースはABIをそろえていますがRust実コンパイルは未検証。Three.js表示のブラウザ実機テストも未実施です。

- 粒子の「季節に応じて自動」モード：春は花びら、夏は蛍、秋は落ち葉、冬は雪（天候のシミュレーションではなく**季節演出**）。既存の手動パーティクル選択やWebGPUフォールバックは維持。
- **サンプルNPC 4人**を村・町に配置。7時に外へ、8時～17時に散歩、17～19時に帰路、19時～7時は屋内扱いで非表示。決定論的スケジュールで、夜間も時計の進行が続きます。**NPCとの会話・家具や建物に対するNPCの衝突判定、屋内のNPC表示は未実装です。**
- 室内の明るさ80％と既存の入退室はそのまま。屋外の季節による照明変化を室内照明にそのまま適用しない設計です。

## 操作

WASD／方向キーで移動、Shiftで走る、Jでジャンプ、Space／Kで攻撃、Eで入退室。タッチ操作ボタンは常時表示、設定パネルは**初期状態で折りたたみ**です。

設定 → WORLD TIME で以下を操作できます。

- ゲーム内の時刻、進行速度（0.25／1／4／8／12／18／24／36倍）、停止・再開、翌朝6:00
- 1季節の日数（1〜365日、初期値1日）
- 「次の季節へ進む」「春の1日目に戻す」
- HUDに季節・年・季節内日数を表示

設定 → ATMOSPHERE / GPU PARTICLES の「季節に応じて自動」を選ぶと季節の粒子を使用します。手動選択も可能です。

## 開発・ビルド

```bash
./build.sh c              # C → WASM＋index.html
./build.sh rust           # Rust → WASM＋index.html（Rust開発環境が必要）
./build.sh assets         # コンパイル済みWASMを使いHTMLを再構成
node tests/test_world_clock.mjs
node tests/test_time_rates.mjs
node tests/test_seasons_npcs.mjs
```

- `src/world-clock.mjs` — 時刻・日付と保存用データの計算
- `src/world-seasons.mjs` — 季節カレンダー、日照、NPCの時間別行動（Three.js非依存）
- `src/engine.c`／`src/lib.rs` — WASM移動・衝突・高低差（変更なし）
- `src/door-logic.mjs` — 18軒の家の出入りと室内の当たり判定
- `index.template.html` — 描画・UI・季節・NPCの組み込み元
- `index.html` — WASM、JSモジュール、仮スプライト画像をビルド時に内蔵
